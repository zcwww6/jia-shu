## 3. 采用方案

采用“精确收口”方案：逐项审计工作区、stash 和已合并分支，只迁移仍有效的内容，不整体提交旧工作区，也不把旧实现作为归档继续留在现行文档中。

未采用的方案：

- 整体提交当前工作区：会重新引入已被否决的 KV/Vercel 部署策略；
- 全部归档保留：会继续制造多个互相冲突的现状来源；
- 仅做文档修补：无法解决未提交演示数据、旧分支和 stash 的持续漂移。

## 5. 安全顺序

1. 比较当前工作区、`stash@{0}`、`develop` 和旧功能分支，生成内容去向清单；
2. 先写并运行演示数据/交互的失败测试；
3. 迁移最小演示实现并使测试转绿；
4. 建立唯一现状文档并修正 README、历史快照和 Docker 设计状态；
5. 搜索现行文档中的旧部署关键词，人工判断每处是历史引用还是错误的当前说明；
6. 执行全量自动验证和 Docker 健康检查；
7. 再次比较 stash，确认无独有有效内容；
8. 提交内容后清理本地分支、worktree、远程旧功能分支和 stash；
9. 复核保留分支、远程同步状态、工作树状态和 Docker 服务状态。

## 6. 失败处理

- stash 中存在尚未迁移的有效内容：停止删除 stash，先把内容归类并迁移；
- 新增测试没有按预期失败：修正测试，使其确实验证新增行为；
- 测试、lint、build 或 Compose 检查失败：停止 Git 清理，修复后重新完整验证；
- worktree 被 Windows 进程占用：先安全删除 Git worktree 注册和已合并分支，记录物理残留路径，待占用解除后删除；
- 远程分支删除失败：保留已经通过验证的本地提交，单独报告远程清理失败，不强推、不回滚主线；
- 发现真实密钥或环境文件进入暂存区：立即停止提交，移除敏感文件并重新检查历史和差异。

## 7. 提交与审查边界

实施阶段至少拆成两个可独立审查的提交：

1. 演示数据、主星系光点及其测试；
2. 唯一现状文档、README 和历史/设计状态修正。

Git 分支、worktree、stash 的删除属于验证后的仓库维护动作，不伪装成代码提交。每个代码/文档提交都先做针对性验证，最终再做全量验证和代码审查。

## 8. 验收标准

- 新增演示内容有自动化测试保护；
- `npx pnpm prisma generate` 成功；
- 全部测试通过；
- lint 通过；
- Next.js 生产构建通过；
- `docker compose --env-file .env.docker config --quiet` 通过；
- PostgreSQL、App、Nginx healthy，live、ready 和首页返回 200；
- 现行文档对本地 Docker、PostgreSQL、Auth.js、Resend 和 Mock 边界描述一致；
- 当前文档不把 Vercel、KV、本地 JSON、云服务器或云 RDS 描述为现行方案；
- 历史快照有明确历史标识和当前状态链接；
- `.env.docker`、`.env.local` 和真实密钥没有进入 Git；
- stash 删除前完成内容去向审计；
- 已合并旧功能分支和旧 worktree 清理完成，或对 Windows 文件锁导致的物理残留给出准确记录；
- 实施分支干净并进入标准审查与集成流程。

# 家书星球上线基础版设计方案

**日期**：2026-07-03

**目标**：基于当前 Next.js 主线代码，将项目从“可演示闭环”推进到“可对外小范围真实用户试用”的上线基础版，同时保持后续功能扩展时的可维护性。

## 1. 当前实际进展基线

当前代码已经具备一条可演示主线：

`/galaxy -> 点亮记忆 -> AI 抽取 -> 共鸣扫描 -> 家书生成 -> 分享确认 -> /share/[token]`

当前主线的真实能力：

- 已有 Next.js App Router 页面与 API 路由
- 已有星系工作台与星球漫游演示壳
- 已有 AI 抽取、家书生成的真实模型接入开关
- 已有最小分享发布与公开分享页
- 已有基础测试、lint、build 工程框架

当前主线的主要限制：

- 无真实用户系统，仍以匿名演示语境为主
- 无数据库，主体数据仍以 Mock 和 localStorage 为主
- 无对象存储，图片和语音能力尚未产品化
- 共鸣识别仍以 Mock 规则为主
- 星系 UI 主页面承担过多状态和演示逻辑，可维护性不足

## 2. 本次上线目标定义

本次不是完整商业产品上线，而是“可对外小范围真实用户试用”的上线基础版。

验收标准：

1. 用户可真实注册、登录、退出
2. 用户可拥有自己的星系和至少一个家庭成员星球
3. 用户可通过文字、图片、语音录入记忆
4. 记忆可被 AI 抽取并经用户确认后持久化
5. 系统可基于真实数据给出共鸣候选
6. 用户可生成家书、确认分享范围，并获得真实可访问链接
7. 数据、媒体、分享链接、权限在刷新、重新登录、换设备后仍成立

最小真实闭环：

`注册登录 -> 创建我的星球/妈妈星球 -> 录入文字/图片/语音记忆 -> AI 抽取并确认 -> 扫描共鸣 -> 生成家书 -> 分享前确认 -> 打开分享页`

## 3. 本次明确不做

为确保范围收敛，本次上线基础版不做以下内容：

- 多人实时协作
- 复杂家谱图谱
- PDF 导出
- 完整主题工坊
- 运营后台完整版
- 高复杂度推荐系统
- 多人共创审核流

这些能力保留到后续 P1/P2。

## 4. 推荐技术路线

采用混合方案：

- 认证：Auth.js
- 关系型数据库：Postgres
- 对象存储：Supabase Storage
- Web 主框架：Next.js App Router
- AI 能力：保留当前 `src/server/ai/*` 路由与 fallback 结构

推荐原因：

1. 与当前代码主线兼容性最好，不需要推翻已有 Next.js 全栈结构
2. 能够最小改造完成真实用户、真实持久化、真实媒体能力
3. 为后续继续扩展更多功能保留清晰边界

## 5. 架构设计

### 5.1 分层结构

#### A. App / Route 层

位置：

- `src/app/*`

职责：

- 页面路由
- 页面级服务端取数
- 鉴权入口
- API route 入口

约束：

- 不承载复杂业务编排

#### B. Feature UI 层

位置：

- `src/features/galaxy/*`
- `src/features/planet/*`
- `src/features/demo-loop/*`

职责：

- 交互渲染
- 页面内状态
- 组件组合

约束：

- 不直接承担持久化和业务规则决策
- demo-loop 逐步被真实业务模块吸收，不再长期并行发展

#### C. Service 层

新增目录：

- `src/server/services/*`

建议服务：

- `auth.service.ts`
- `galaxy.service.ts`
- `planet.service.ts`
- `memory.service.ts`
- `media.service.ts`
- `resonance.service.ts`
- `book.service.ts`
- `share.service.ts`

职责：

- 业务流程编排
- 权限校验
- 事务边界
- 调用 AI / 数据层 / 存储层

#### D. Data Access 层

新增目录：

- `src/server/db/*`

职责：

- 数据库 schema
- 数据访问封装
- 查询与事务

#### E. AI / Media Integration 层

位置：

- `src/server/ai/*`
- 新增媒体处理适配模块

职责：

- 抽取
- 家书生成
- 语音转写
- 图片元数据辅助提取

约束：

- 由 service 层统一调用，不由页面直接编排

## 6. 核心领域模型

本次上线基础版应最少建立以下真实实体：

### 6.1 用户与身份

- User
- Session / Account
- UserProfile

### 6.2 星系与星球

- Galaxy
- Planet
- PlanetRelation

### 6.3 记忆与素材

- Memory
- MemoryAsset
- MemoryExtractResult
- MemoryConfirmation

### 6.4 共鸣

- ResonanceCandidate
- ResonanceDecision

### 6.5 家书与分享

- BookDraft
- BookSection
- ShareRecord

设计原则：

- 文字、图片、语音最终都归并到统一的 Memory 主体
- 记忆原始素材与 AI 抽取结果分离存放
- 分享配置独立建模，避免把公开逻辑埋在前端状态里

## 7. 上线功能清单

### 7.1 P0：上线必做

#### 1. 用户与身份

- 注册
- 登录
- 退出
- 会话校验
- 受保护页面访问控制
- 演示模式从主线业务中剥离

#### 2. 真实数据持久化

- 用户数据入库
- 星球数据入库
- 记忆数据入库
- 家书与分享数据入库
- 前端 localStorage 退化为草稿缓存

#### 3. 星球创建与管理

- 创建自己、父母、孩子、伴侣四类星球
- 编辑名称、关系、默认可见范围
- `/galaxy` 读取真实星球数据

#### 4. 三通道记忆录入

- 文字录入
- 图片上传
- 语音上传
- 语音转写后进入统一抽取流程
- 图片、音频与记忆实体建立关联

#### 5. AI 抽取与人工确认

- 时间、地点、人物、事件、情绪、摘要抽取
- 用户人工修正
- 抽取失败时允许人工补全
- 确认后持久化

#### 6. 隐私与权限

- 记忆可见范围
- 是否允许参与共鸣识别
- 分享前展示范围确认
- 分享页按配置渲染

#### 7. 共鸣识别

- 基于真实确认记忆生成候选
- 先做规则匹配 + 基础语义增强
- 用户可确认 / 拒绝 / 稍后处理

#### 8. 家书生成

- 只使用已确认来源
- 保留 `sourceMemoryIds`
- 支持重新生成
- 支持发布分享

#### 9. 真实分享

- token 链接跨设备访问
- 分享记录可读取
- 分享可失效或撤回

#### 10. 上线稳定性

- 上传失败提示与重试
- AI 失败 fallback
- 基础审计与错误日志
- `test`、`lint`、`build` 全绿

### 7.2 P1：上线后紧跟

- AI 采访式追问
- embedding / 向量检索升级
- 多人邀请补充记忆
- 分享过期时间与撤回历史
- 最小管理后台
- 埋点与监控
- 更完整的星球内部沉浸编辑

## 8. 阶段推进顺序

### 阶段 1：身份与真实持久化地基

目标：

- 建立真实用户身份
- 建立数据库持久化
- 将本地 json / localStorage 从主存储降级

涉及改造：

- 新增 Auth.js
- 新增 `src/server/db/*`
- 新增 `src/server/services/auth.service.ts`
- 新增 `planet.service.ts`、`memory.service.ts`
- 替换本地分享存储

验收：

- 登录后仅能看到自己的数据
- 数据刷新、重登、换设备仍存在

### 阶段 2：记忆三通道产品化

目标：

- 统一文字、图片、语音为同一记忆模型

涉及改造：

- 升级记忆创建页面
- 增加对象存储上传能力
- 增加语音转写能力
- 记忆与媒体实体建模

验收：

- 用户可上传图片与音频
- 音频可转写并继续抽取
- 一条记忆可挂载素材

### 阶段 3：共鸣与家书真实闭环

目标：

- 让共鸣与家书从演示数据切换到真实用户数据

涉及改造：

- 抽离真实 `resonance.service.ts`
- 共鸣页读真实候选
- 家书草稿与分享记录入库
- 分享页走数据库读取

验收：

- 共鸣候选来自真实确认记忆
- 家书来源可追溯
- 分享跨设备稳定访问

### 阶段 4：星系主界面主线收编

目标：

- 将 `/galaxy` 从演示壳升级为真实用户主工作台

涉及改造：

- 拆分 `galaxy-workspace.tsx`
- 用真实数据替换默认 mock 展示
- 将 demo-loop 能力内嵌为正式 workflow

验收：

- `/galaxy` 成为真实主入口
- demo 路由仅保留为回归/演示辅助

## 9. 对当前代码的具体影响

### 9.1 需要保留并升级的模块

- `src/server/ai/ai-client.ts`
- `src/server/ai/openai-client.ts`
- `src/app/api/ai/extract/route.ts`
- `src/app/api/books/generate/route.ts`
- `src/app/api/books/publish/route.ts`
- `src/app/share/[token]/page.tsx`

这些模块已经是主线基础，应升级为真实业务入口，而不是废弃。

### 9.2 需要降级为演示或测试用途的模块

- `src/shared/mock/*`
- `src/features/demo-loop/storage.ts`
- demo session 相关默认数据

这些模块后续仍可保留，但不应继续作为主流程数据来源。

### 9.3 需要重点治理的可维护性风险

#### A. `galaxy-workspace.tsx` 过大

问题：

- 状态过多
- 演示逻辑、UI 逻辑、业务流程逻辑混杂

要求：

- 后续拆为 scene、overlay、actions、selectors 等更小单元

#### B. 业务逻辑分散在 route / page / component

问题：

- 后续难以扩展
- 测试困难

要求：

- 所有关键写操作统一经 service 层

#### C. Mock 与真实逻辑边界不清

问题：

- 演示状态容易污染真实产品路径

要求：

- 明确 production / demo 的数据入口边界

## 10. 可维护性原则

为保证后续还能继续补充更多功能，本方案设定以下硬约束：

1. 不再继续增加超大页面文件
2. 所有业务写入必须先经过 service 层
3. Mock 数据仅用于测试与受控演示
4. 新功能必须至少覆盖 service 测试和关键 route 测试
5. 分享、权限、媒体都必须以明确字段建模
6. 前端状态只能做交互缓存，不能继续充当主业务真相来源

## 11. 最终结论

当前项目最强的价值在于已经拥有一条完整且有感染力的产品主线。接下来的正确方向不是继续扩写演示 UI，而是把：

- 用户
- 数据
- 媒体
- 权限
- 分享

这五层地基补实。

只要完成这五层，再把现有星系 UI 主线接上真实数据，项目就能从“漂亮的演示工程”进入“可真实试用的上线基础版”。

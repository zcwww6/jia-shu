# 家书星球部署与数据库方案（演示优先版）

**日期**：2026-07-04

**目标**：为当前已完成 Phase 1 地基的家书星球项目确定一套“可演示、可上线、可继续演进”的部署方案，重点解决应用部署方式、数据库选型、Prisma 迁移策略、最小运维边界与上线检查流程。

## 1. 当前上下文

当前主线代码已经完成以下基础能力：

- Auth.js 登录链路与受保护路由
- Prisma 7 + PostgreSQL 数据访问基础
- `/galaxy` 认证加载与个人星系引导
- 分享页改为数据库主存储，保留旧文件分享只读兼容
- `test`、`lint`、`build` 通过

当前最缺的不是页面能力，而是**一套稳定、简单、适合演示上线的真实部署方案**。

本方案约束如下：

- 应用部署到**国内云厂商云服务器**
- 部署方式使用 **Docker**
- 数据库以“最终可演示、可上线”为目标，不采用自建数据库
- 方案优先级是**稳、快、少运维**

## 2. 方案比较

### 方案 A：国内云服务器 + 海外托管 PostgreSQL

例如：

- 应用：阿里云 / 腾讯云 ECS
- 数据库：Neon / Supabase Postgres

优点：

- 接入非常快
- 与 Prisma 配合顺滑
- 运维成本低

缺点：

- 国内到海外数据库链路不稳定
- 演示时容易出现网络抖动
- 延迟与可用性不可控

结论：

- 不适合作为当前项目的最终演示方案

### 方案 B：国内云服务器 + 同云厂商 RDS PostgreSQL

例如：

- 应用：ECS / CVM
- 数据库：阿里云 RDS PostgreSQL / 腾讯云 PostgreSQL

优点：

- 网络最稳定
- 数据库备份、恢复、监控、高可用由云厂商负责
- 安全组与内网访问配置清晰
- 后续从演示版走向正式生产更平滑

缺点：

- 初始化比 Neon 多一点配置
- 成本略高于自建数据库

结论：

- **本项目当前阶段的推荐方案**

### 方案 C：国内云服务器 + Docker 自建 PostgreSQL

优点：

- 成本最低
- 当下最灵活

缺点：

- 备份、恢复、升级、故障全部自担
- 容器卷、数据盘、冷备策略都要自己维护
- 演示可用并不等于长期稳

结论：

- 只适合临时测试，不适合作为当前项目的最终演示版

## 3. 最终推荐方案

**推荐方案：国内云服务器 + Docker Compose + Nginx + 同云厂商 RDS PostgreSQL**

目标形态：

- 1 台云服务器承载 Web 应用
- 1 个托管 PostgreSQL 实例承载真实数据
- 数据库不进入 Docker，不与应用共机自建

推荐原因：

1. 最符合“可演示、可上线、少运维”的目标
2. 与当前 `Next.js + Auth.js + Prisma` 主线兼容最好
3. 后续要接对象存储、监控、后台、更多 AI 能力时无需重做基础设施

## 4. 部署拓扑

### 4.1 逻辑拓扑

```text
公网用户
  ->
Nginx / HTTPS
  ->
Next.js App Container
  ->
RDS PostgreSQL
```

### 4.2 云上资源

最小部署单元：

- **1 台云服务器**
  - Docker Engine
  - Docker Compose
  - Nginx 容器
  - App 容器
- **1 个 RDS PostgreSQL 实例**
  - 打开自动备份
  - 仅允许云服务器来源访问

### 4.3 网络原则

- 80 / 443 对公网开放
- 应用容器不直接暴露高位端口到公网
- PostgreSQL 端口仅对白名单 IP 或同 VPC 开放
- 优先使用同地域部署，减少链路波动

## 5. Docker 部署结构

推荐采用：

- `docker-compose.yml`
- `Dockerfile`
- `.env.production` 或服务器环境变量注入

容器职责：

### `app`

职责：

- 运行 Next.js 生产服务
- 读取 `DATABASE_URL`、`AUTH_SECRET`、`AUTH_RESEND_*`

要求：

- 启动前镜像内已完成依赖安装和构建
- 容器启动命令仅运行生产服务，不做开发态构建

### `nginx`

职责：

- 监听 80 / 443
- TLS 终止
- 转发到 `app`

要求：

- 提供 HTTPS
- 提供基本静态压缩与反向代理

## 6. 数据库设计决策

### 6.1 选型结论

数据库使用：

- **PostgreSQL**
- **托管 RDS**

不采用：

- SQLite 作为线上主库
- Docker 自建 PostgreSQL
- 海外托管库作为正式演示主库

### 6.2 原因

当前项目已有：

- Auth.js 用户与会话
- Galaxy / Planet / SharedBook 等结构化数据
- 后续还会继续增加 Memory / Asset / Resonance / Book 等实体

这类数据天然适合 PostgreSQL。

## 7. 环境变量清单

线上至少需要：

```bash
DATABASE_URL=
AUTH_SECRET=
AUTH_RESEND_API_KEY=
AUTH_RESEND_FROM=
```

如开启真实模型：

```bash
OPENAI_API_KEY=
OPENAI_MODEL=
OPENAI_BASE_URL=
```

要求：

- 应用配置由服务器环境或部署平台注入
- 不把生产密钥写死在镜像里
- 不提交 `.env.production`

## 8. Prisma 迁移策略

### 8.1 开发环境

本地开发继续使用：

```bash
npx pnpm prisma migrate dev
```

### 8.2 生产环境

生产环境只使用：

```bash
npx pnpm prisma migrate deploy
```

明确禁止：

- 在生产容器里跑 `migrate dev`

### 8.3 推荐发布顺序

1. 构建应用镜像
2. 推送镜像到镜像仓库
3. 云服务器拉取新镜像
4. 执行 `prisma migrate deploy`
5. 启动或重启 `app` 容器
6. 通过 Nginx 对外提供服务

## 9. 最小运维策略

### 9.1 备份

起步要求：

- 打开 RDS 自动备份
- 备份保留期至少 7 天

### 9.2 安全

- 数据库不暴露给公网任意 IP
- `AUTH_SECRET` 使用真实随机值
- 邮件服务密钥单独保管

### 9.3 日志

当前阶段足够：

- Docker 容器日志
- Nginx 访问日志

暂不强制要求：

- Prometheus / Grafana
- 全链路 tracing

### 9.4 可恢复性

至少保证：

- 云服务器重启后容器可拉起
- RDS 备份可恢复
- 迁移记录由 Prisma 管理

## 10. 上线检查清单

上线前必须确认：

### 环境

- 云服务器已安装 Docker / Compose
- 域名已解析到云服务器
- HTTPS 已配置
- RDS 已创建并可从应用网络访问

### 配置

- `DATABASE_URL` 正确
- `AUTH_SECRET` 正确
- `AUTH_RESEND_API_KEY` / `AUTH_RESEND_FROM` 正确

### 数据库

- `npx pnpm prisma migrate deploy` 成功
- `npx pnpm prisma generate` 已在构建流程中处理

### 应用功能

- 未登录访问 `/` 可进入登录流程
- 登录后可进入 `/galaxy`
- 首次登录可完成个人星系引导
- 发布家书可成功生成 `/share/[token]`
- 分享链接可访问

## 11. 当前阶段外部阻塞

当前代码侧已经具备上线基础，但还有一个外部环境阻塞没有在本地完成：

- 未在当前 worktree 中执行 `prisma migrate dev --name auth_persistence_baseline`

阻塞原因：

- 当前 worktree 没有 `.env.local`
- 当前 shell 没有 `DATABASE_URL`
- 没有安全可用的真实本地 Postgres 目标可供迁移

这不是代码问题，而是环境未接通。

## 12. 下一步执行建议

按优先级建议如下：

1. 在国内云厂商创建 **RDS PostgreSQL**
2. 在同地域创建 **云服务器**
3. 用 Docker Compose 部署当前主线应用
4. 配置生产环境变量
5. 执行 `prisma migrate deploy`
6. 手工验证登录、进入星系、发布家书、打开分享页

## 13. 最终结论

对当前项目而言，**最终可演示且可上线的最佳数据库方案不是自建，而是同云厂商托管 PostgreSQL RDS**。

最合适的整体组合是：

- **国内云服务器**
- **Docker Compose**
- **Nginx**
- **RDS PostgreSQL**
- **Prisma migrate deploy**

这套方案比“自建数据库”更稳，比“海外托管库”更适合国内演示，也不会把后续扩展能力锁死。

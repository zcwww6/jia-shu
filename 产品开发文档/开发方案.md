# 家书星球系统规划方案  
## 40 天单兵作战版：前后端框架、AI 框架与项目进度规划

---

## 一、规划目标

### 1.1 项目目标

家书星球是一款 AI 原生家庭记忆产品。项目目标不是在 40 天内完成完整商业产品，而是完成一个**可运行、可演示、可讲清商业价值的 MVP 闭环**。

MVP 必须证明以下核心能力：

1. 用户可以进入“我的星系”主工作台，看到家庭成员星球和推荐航线。
2. 用户可以靠近一颗星球，并进入星球内部漫游。
3. 用户可以通过文字、语音或图片点亮一颗记忆星。
4. AI 可以对记忆进行采访、追问和结构化抽取，并生成可确认的记忆星。
5. 系统可以识别两颗星球之间的共同记忆，并点亮共鸣星轨。
6. 用户确认共鸣后，AI 可以在家书工坊生成一页有来源的家书。
7. 系统可以生成一个可预览、可分享、分享前可确认范围的家书页面。

### 1.2 参赛交付目标

40 天结束时，至少交付以下内容：

| 交付物         | 说明                                             |
| -------------- | ------------------------------------------------ |
| 可运行 Web MVP | 可通过浏览器访问并完成核心流程                   |
| 演示数据       | 至少包含 2 个星球、6—10 条记忆、2 个共同记忆案例 |
| AI 采访 Demo   | 展示 AI 如何追问、抽取、整理记忆                 |
| 共鸣星轨 Demo  | 展示 AI 如何点亮共鸣星轨并生成家书线索           |
| 家书预览页     | 展示最终成果物                                   |
| 项目答辩 PPT   | 说明产品价值、技术架构、商业模式、进度成果       |
| Demo 视频      | 2—4 分钟，展示完整用户路径                       |
| 开发记录       | Git commit、部署记录、模型调用记录、截图记录     |

### 1.3 单兵作战约束

本项目必须遵守以下约束：

1. **不做原生 App**  
   只做 Web App，移动端用响应式页面适配。

2. **不自建复杂后端集群**  
   前期用 Next.js 全栈能力 + 托管数据库，减少运维成本。

3. **不引入过多中间件**  
   MVP 阶段不引入 Neo4j、Qdrant、Kafka、复杂任务编排系统。

4. **不做实时多人协作**  
   家庭成员可通过邀请链接补充内容，但不做多人同时编辑。

5. **不做复杂视频处理**  
   MVP 支持文字、语音、图片，视频仅作为后续扩展。

6. **不对接实体印刷供应链**  
   只做网页纪念册和 PDF 导出预留。

7. **AI 成本必须可控**  
   通过短文本、缓存、结构化输出、减少重复调用控制模型成本。

| 点亮记忆星 | 图片上传                       | 可上传并保存图片               |

| 隐私授权 | 是否允许交集识别                 | 每条记忆可设置                 |
| 分享     | 分享家书链接                     | 可用公开 token 实现            |

### 2.2 延后到 P1 的功能

| 功能             | 延后原因                       |
| ---------------- | ------------------------------ |
| PDF 导出         | 若时间允许再做，网页家书优先   |
| 家庭三人以上星系 | 双人星系先跑通                 |
| 主题星云         | 可以用标签聚合做弱实现         |
| 星球工坊         | 背景、材质、星环保存可后置     |
| 自动巡航         | 推荐航线动画演示可后置         |
| 微信分享优化     | MVP 用普通链接即可             |
| 邮件 / 短信邀请  | 先用复制链接                   |
| 老照片修复       | AI 成本高，非核心闭环          |
| 复杂图谱可视化   | 视觉加分但开发成本高           |

### 2.3 明确不做的功能

| 功能                   | 不做原因               |
| ---------------------- | ---------------------- |
| 原生 iOS / Android App | 单兵 40 天不可控       |
| 实时协同编辑           | 技术复杂度高           |
| 实体印刷下单           | 供应链复杂             |
| 复杂家谱图             | 和核心 AI 闭环关系不强 |
| 视频剪辑               | 多媒体成本高           |
| 完整支付系统           | 参赛阶段不需要         |
| 商业运营后台           | MVP 不需要             |

## 三、系统整体架构

### 3.1 总体架构原则

系统采用“前端全栈一体化 + 托管数据库 + 轻量 AI 编排”的架构。

核心原则：

1. **一个代码仓库完成前后端**
2. **一个数据库承载业务数据与向量数据**
3. **一个对象存储承载图片和音频**
4. **一个 AI Gateway 统一管理模型调用**
5. **少量脚本和定时任务处理异步逻辑**
6. **以演示闭环为目标，不追求复杂扩展性**

### 3.2 系统架构图

```text
用户浏览器
  ↓
Next.js Web App
  ├── 页面层：Galaxy / Planet Roaming / Memory Star / Resonance Track / Themes / Book Workshop
  ├── Server Actions：表单提交、轻量写入
  ├── Route Handlers：AI 调用、文件处理、分享链接、交集识别
  ↓
业务服务层
  ├── User Service
  ├── Planet Service
  ├── Memory Service
  ├── Interview Service
  ├── Extraction Service
  ├── Embedding Service
  ├── Intersection Service
  ├── Story Service
  └── Book Service
  ↓
数据与存储层
  ├── PostgreSQL
  ├── pgvector
  ├── Object Storage
  └── Local / Remote Cache
  ↓
AI 能力层
  ├── LLM 文本模型
  ├── Embedding 模型
  ├── 语音转写模型
  ├── 图像理解模型
  └── Prompt / Schema / Guardrail
```

### 3.3 技术栈总览

| 层级       | 推荐方案                    | 选择理由                               |
| ---------- | --------------------------- | -------------------------------------- |
| 前端框架   | Next.js App Router          | 页面、接口、服务端渲染一体化，适合单兵 |
| UI 框架    | Tailwind CSS + shadcn/ui    | 开发快，视觉一致性强                   |
| 动效       | Framer Motion               | 用于星球、星轨、卡片动效               |
| 状态管理   | Zustand                     | 简单轻量，用于跨页面临时状态           |
| 表单       | React Hook Form + Zod       | 表单校验稳定，适合结构化数据           |
| 后端接口   | Next.js Route Handlers      | 避免单独搭 NestJS                      |
| 数据库     | PostgreSQL                  | 承载用户、星球、记忆、权限             |
| 向量检索   | pgvector                    | MVP 阶段无需额外向量库                 |
| 文件存储   | Supabase Storage / S3 / OSS | 存储图片、音频和导出文件               |
| ORM        | Prisma 或 Drizzle           | 单兵开发建议二选一，不重复引入         |
| AI 调用    | AI Gateway 封装             | 统一模型调用、日志、成本控制           |
| 部署       | Vercel + 托管数据库         | 前期部署简单，减少运维                 |
| 版本管理   | GitHub                      | 保存开发凭证                           |
| 原型与设计 | Figma / HTML 原型           | 用于答辩展示                           |

## 四、前端框架设计

### 4.1 前端目标

前端不是简单页面展示，而要承担完整用户任务流：

1. 让用户进入“我的星系”，把家庭星球作为主操作界面。
2. 引导用户沿推荐航线靠近星球，而不是只进入表单流程。
3. 降低记忆录入门槛，将录入结果呈现为记忆星。
4. 展示星球内部漫游、时间轨迹和故事星节点。
5. 呈现共鸣星轨的情感冲击和来源对比。
6. 让家书成为一次漫游后的最终交付物。

| 星域 | 工程承载方式 | MVP 处理 |
| ---- | ------------ | -------- |
| 我的星系 | `/galaxy` | P0 主工作台 |

| 主题星云 | `/themes` | P1，可先做模板选择 |
| 家书工坊 | `/books/new` | P0 最终生成入口 |

### 4.3 前端核心模块说明

#### 1. 我的星系 `/galaxy`

目标：承载家庭星系主工作台，作为 Demo 和 MVP 的第一屏。

核心能力：

- 展示家庭成员星球、纪念星、公开分享星。
- 展示推荐航线，引导新用户完成一次完整旅程。
- 支持拖拽漫游、滚轮缩放、双击聚焦、双指旋转的基础状态。
- 提供迷你星图、视角控制、长辈大字模式、生成家书入口。
- 点击星球进入 `/planet/[planetId]`，点击共鸣星轨进入 `/resonance`。

#### 2. 星球内部漫游 `/planet/[planetId]`

目标：替代传统个人星球详情页，展示可漫游的人生轨道。

核心能力：

- 展示星球档案、可见范围、记忆星数量、共鸣候选、可生成章节。
- 展示时间轨迹和故事星节点。
- 点击故事星后展示时间、地点、人物、情绪、来源说明。
- 支持“补充视角”“点亮记忆星”“写成家书”等快捷操作。
- 支持进入沉浸模式时收起侧边栏或减少干扰控件。

#### 3. 点亮记忆星 `/memory/new`

目标：保留轻量表单能力，但输出物是记忆星。

输入方式：

- 文字输入。
- 图片上传。
- 音频上传。
- 浏览器录音或手动转写。

交互重点：

- 输入后点击“AI 整理”。
- 生成待确认记忆星。
- 用户确认后进入星球时间轨迹和共鸣候选池。

#### 4. AI 采访 `/interview/[sessionId]`

目标：作为点亮记忆星和补充视角的增强入口。

布局：

- 当前星球信息。
- AI 对话。
- 实时记忆草稿。
- 语音 / 文字输入。

功能：

- AI 提问。
- 用户回答。
- AI 追问。
- 实时提取信息。
- 保存为记忆星。

#### 5. 共鸣星轨 `/resonance`

目标：制造产品 Aha Moment，展示 AI 点亮但尚需家人确认的连接。

展示：

- A 星球记忆。
- B 星球记忆。
- 时间 / 地点 / 人物 / 语义匹配分数。
- AI 判断理由。
- 用户确认按钮。

操作：

- 确认合并。
- 不是同一件事。
- 稍后再看。
- 邀请对方补充。
- 带入家书工坊。

#### 6. 主题星云 `/themes`

目标：让用户从家庭团圆、父母人生、亲子成长、纪念星册、旅行星云、伴侣星云等主题进入家书工坊。

MVP 可以先实现为主题模板选择，不必完成复杂自动聚合。

#### 7. 家书工坊 `/books/new`

目标：选择来源范围、主题语气并生成一页家书。

来源范围：

- 单星球。
- 双星系。
- 家庭星系。
- 纪念星。

输出要求：

- 生成标题、导语、章节和来源说明。
- 保留 `sourceMemoryIds`。
- 生成后跳转 `/books/[bookId]`。

#### 8. 家书预览与分享 `/books/[bookId]`、`/share/[shareToken]`

目标：展示最终成果物，并在公开前确认范围。

模块：

- 封面。
- 星系成员。
- 章节目录。
- 故事正文。
- 照片墙。
- 原始记忆来源。
- 分享确认面板。
- 导出按钮预留。

### 4.5 前端状态设计

MVP 阶段可以使用轻量状态管理：

| 状态              | 存储位置                       |
| ----------------- | ------------------------------ |
| 当前用户          | 服务端 session / Supabase Auth |
| 当前星球          | URL + 服务端查询               |
| 录入中的记忆草稿  | Zustand / localStorage         |
| AI 采访临时上下文 | 数据库 interview_sessions      |
| 纪念册编辑草稿    | 数据库 book_drafts             |
| Toast / 弹窗      | 前端本地状态                   |
| 星系视角          | Zustand / URL search params    |
| 当前星域          | URL path + 前端本地状态        |
| 推荐航线进度      | Zustand / localStorage         |
| 星球漫游焦点      | URL + 前端本地状态             |
| 沉浸模式          | 前端本地状态                   |
| 长辈大字模式      | localStorage                   |
| 分享确认范围      | 数据库 book_shares / 前端草稿  |

关键交互状态包括：

- 视角缩放：记录 zoom、panX、panY。
- 拖拽漫游：区分空白拖拽和星球点击，避免事件冲突。
- 旋转：移动端支持双指旋转，桌面端可先降级为固定角度。
- 聚焦：双击星球后更新 focusedPlanetId 并显示进入漫游入口。
- 自动巡航：P1，可按推荐航线逐步聚焦星球和共鸣星轨。
- 沉浸模式：进入星球内部漫游时减少侧边导航干扰。
- 长辈大字模式：提升字号、按钮尺寸和可点击区域。
- 分享确认弹层：公开前必须确认正文、来源标题、原始全文的展示范围。

### 4.6 响应式与适老化要求

移动端不强行复刻桌面侧边栏。小屏应保留顶部或底部下拉导航，至少覆盖 8 个星域入口：我的星系、隐私星域、纪念星域、星球工坊、记忆星群、共鸣星轨、主题星云、家书工坊。

长辈大字模式需要同时调整：

- 字号提升到默认模式的 1.15—1.3 倍。
- 主要按钮高度不低于 44px。
- 可点击星球、记忆星、故事节点的触控区域不低于 44px。
- 减少细碎动效和复杂手势依赖，保留明确的“返回星系”“点亮记忆星”“分享前确认”按钮。

## 五、后端框架设计

### 5.1 后端目标

后端负责：

1. 用户、星球、记忆、星系、家书的数据管理。
2. 文件上传与访问控制。
3. AI 调用封装。
4. 记忆结构化抽取。
5. embedding 生成与保存。
6. 共同记忆识别。
7. 家书生成。
8. 分享链接与权限校验。

### 5.2 后端实现策略

为了降低开发成本，MVP 不单独搭建 NestJS 后端，而是在 Next.js 中实现后端接口：

```text
app/api/
  ai/
    interview/route.ts
    extract/route.ts
```

1. 原始内容必须保留。

3. AI 生成结果必须可追溯。
4. 每条记忆必须有独立隐私设置。

## 七、AI 框架设计

### 7.1 AI 总体定位

家书星球中的 AI 不是一个聊天机器人，而是四个角色的组合：

1. **采访者**：主动提出问题，帮助用户回忆细节。
2. **整理者**：把语音、文字、图片整理成结构化记忆。
3. **连接器**：发现不同星球之间的共同记忆。
4. **编排者**：把多条已确认记忆生成有来源的家书。

```text
  ├── Interview Agent
```

### 7.3 AI 调用策略

为了控制成本，AI 不应在每个页面频繁调用，而应只在关键节点调用。

| 场景                     | 是否调用 AI | 说明                                 |
| ------------------------ | ----------- | ------------------------------------ |
| 用户打开我的星系         | 否          | 读取星球与演示数据，不自动调用 AI     |
| 创建星球                 | 否 / 可选   | 默认模板即可                         |
| 录入文字记忆             | 是          | 调用抽取模型                         |
| 上传图片                 | 可选        | MVP 可先用户手填，若有余力接图像理解 |
| 上传语音                 | 是          | 调用语音转写                         |
| AI 采访每轮对话          | 是          | 但限制轮数                           |
| 记忆入库后生成 embedding | 是          | 用于检索                             |
| 用户查看星球内部漫游     | 否          | 数据库读取故事星节点                 |
| 扫描共同记忆             | 部分是      | 先规则筛选，再向量检索               |
| 生成共鸣星轨判断理由     | 是          | 输出可解释的匹配理由                 |
| 生成家书                 | 是          | 核心生成，必须保留 sourceMemoryIds   |

### 7.6 交集识别算法

MVP 使用规则 + 向量混合评分，不做复杂机器学习。

评分维度：

| 因子              | 权重 |
| ----------------- | ---: |
| 时间接近度        |  25% |
| 地点一致性        |  20% |
| 人物重合度        |  20% |
| 语义相似度        |  25% |
| 主题 / 情绪相似度 |  10% |

伪代码：

```python
final_score = (
  time_score * 0.25 +
  location_score * 0.20 +
  people_score * 0.20 +
  semantic_score * 0.25 +
  topic_score * 0.10
)

if final_score >= 0.75:
    status = "high_confidence"
elif final_score >= 0.60:
    status = "medium_confidence"
else:
    status = "ignore"
```

### 7.7 AI 防幻觉机制

1. AI 生成家书前，只读取已确认记忆。
2. 所有生成家书都保存 sourceMemoryIds。
3. 家书页面展示“来源记忆”。
4. 用户可以编辑 AI 生成文案。
5. 未确认的抽取结果不能进入家书。
6. 不确定日期必须标注为不确定。
7. 敏感内容默认不参与公开分享。

### 7.8 AI 成本控制策略

| 策略                 | 说明                                 |
| -------------------- | ------------------------------------ |
| 限制采访轮数         | MVP 每次采访最多 5—8 轮              |
| 短文本优先           | 每次只传当前记忆和必要上下文         |
| 抽取和生成分离       | 抽取用低成本模型，故事生成用较强模型 |
| embedding 只生成一次 | 记忆修改后才重新生成                 |
| 缓存 AI 结果         | 同一记忆不重复抽取                   |
| 演示数据预生成       | 答辩时减少现场 AI 调用风险           |
| 记录 token 日志      | 每次调用记录成本                     |
| 图片理解可降级       | 若成本高，图片先只上传，不强制识别   |

### 8.2 成本控制目标

40 天开发期建议将资源成本控制在：

| 成本项      | 控制策略                 |
| ----------- | ------------------------ |
| 服务器      | 优先使用免费或低价托管   |

建议目标：**开发期资源成本控制在 0—300 元人民币以内**。如果需要更稳定的部署和备用模型，可放宽到 500 元以内。

| PDF 生成失败       | 只展示网页家书                   |

## 十七、风险与应对

### 17.1 技术风险

| 风险                   | 应对                                    |
| ---------------------- | --------------------------------------- |
| AI JSON 输出不稳定     | 使用 Zod 校验，失败后重试或进入手动编辑 |

| 部署失败               | 准备本地运行版本和录屏                  |
| PDF 导出延期           | 网页家书作为核心交付                    |

### 17.2 产品风险

| 风险                   | 应对                         |
| ---------------------- | ---------------------------- |

| 交互复杂               | 用线性流程引导用户           |

| 部署成本上升    | 优先免费 / 低价方案                |

## 十八、最终推荐技术组合

### 18.1 首选组合

```text
前端：Next.js App Router + Tailwind CSS + shadcn/ui + Framer Motion
后端：Next.js Route Handlers + Server Actions
数据库：Supabase PostgreSQL
向量：pgvector
存储：Supabase Storage
ORM：Prisma
AI：统一 AI Gateway，接入文本模型、embedding 模型、语音转写
部署：Vercel
版本管理：GitHub
设计：Figma + HTML 原型
```

### 18.2 为什么不建议一开始使用 NestJS + Qdrant + Neo4j

| 技术           | MVP 阶段不优先的原因                |
| -------------- | ----------------------------------- |
| NestJS         | 单兵开发会增加前后端联调和部署成本  |
| Qdrant         | MVP 数据量小，pgvector 足够验证闭环 |
| Neo4j          | 双人星系不需要复杂图数据库          |
| Redis / BullMQ | 任务量小，可先同步或轻量异步        |
| React Native   | Web 响应式足够参赛演示              |
| 微服务         | 不符合 40 天单兵作战约束            |

### 18.3 后续升级路径

当 MVP 验证成功后，可按以下顺序升级：

1. 增加 PDF 导出。
2. 接入微信小程序。
3. 引入异步任务队列。
4. 引入 Qdrant 提升向量检索。
5. 引入 Neo4j 做复杂家庭关系图谱。
6. 接入支付和订阅。
7. 对接实体印刷供应链。
8. 建设运营后台。

## 十九、答辩表达建议

### 19.1 技术表达

可以这样向评委解释技术方案：

> 为了保证 40 天单兵作战可交付，我们没有一开始引入复杂微服务、独立向量库和图数据库，而是采用 Next.js 全栈框架、PostgreSQL、pgvector 和对象存储，先把星系主工作台、星球内部漫游、记忆抽取、共同记忆识别和家书生成这个核心闭环跑通。后续当数据量和关系复杂度上升后，再平滑升级到 Qdrant、Neo4j 和独立后端服务。

### 19.2 AI 原生表达

> 家书星球的 AI 不是简单生成文案，而是在产品流程中承担采访者、整理者、连接器和编排者四个角色。它先帮助用户点亮记忆星，再将记忆结构化，之后识别家庭成员之间的共同经历并点亮共鸣星轨，最终生成可分享的家书。

### 19.3 成本控制表达

> 本项目在 MVP 阶段坚持低成本架构：一个 Web 项目、一个数据库、一个文件存储、一套 AI 调用封装。通过限制模型调用轮数、缓存 AI 结果、只对确认记忆生成 embedding 等方式，将资源成本控制在可接受范围内。

### 19.4 闭环表达

> 只要用户能进入家庭星系，进入星球内部漫游，点亮两段相关记忆，AI 能识别它们属于同一个家庭事件，并生成一页家书，就证明了产品最核心的商业与技术闭环。

## 二十、总结

40 天单兵作战的关键不是“做全”，而是“做准”。

家书星球的 MVP 应该牢牢围绕一个核心场景：

> 两个家庭成员，各自点亮一颗记忆星；AI 发现它们之间的共同经历，并生成一份有情感、有来源、可分享前确认范围的家书。

因此，本项目的最优技术路线是：

1. 使用 Next.js 完成前后端一体化开发。
2. 使用 PostgreSQL + pgvector 承载业务数据和向量检索。
3. 使用对象存储保存图片和音频。
4. 使用统一 AI Gateway 管理采访、抽取、embedding 和故事生成。
5. 用规则 + 向量混合方式实现共同记忆识别。
6. 用网页家书完成最终交付。
7. 将复杂图谱、PDF、App、印刷、支付全部后置。

最终交付不是一个功能堆砌的半成品，而是一个完整、清晰、可演示的 AI 原生家庭记忆闭环。
